# AGENTS.md — инструкции ИИ-агенту Geometry Dash Generator

> Цель: генерация **красивых, разнообразных, понятных и проверяемо проходимых** редактируемых уровней Geometry Dash 2.209+, а не только синтаксически правильных файлов. Язык задач и отчётов — русский. Обновлено: 2026-11-06.

## Прочитать перед работой (порядок)

1. Этот файл — правила, возможности и ограничения **текущего проекта**.
2. [docs/OBJECT_CATALOG.md](docs/OBJECT_CATALOG.md) — семейства игровых объектов, конкретные ID, справочники всех остальных ID.
3. [docs/TRIGGER_CATALOG.md](docs/TRIGGER_CATALOG.md) — семейства триггеров, подтверждённые ID, параметры, шаблоны и ограничения.
4. [docs/FORMAT.md](docs/FORMAT.md) — сериализация объектов, цвета, .gdlvl и сохранения.
5. [docs/RESEARCH.md](docs/RESEARCH.md) и [PROGRESS.md](PROGRESS.md) — проверка совместимости, прогресс и известные проблемы.
6. Код: `gdgen/spec.py`, `gdgen/generator.py`, `gdgen/objects.py`, `gdgen/level.py`, `gdgen/route.py`, `gdgen/validate.py`, `gdgen/preview.py`, `gdgen/city.py`.

**Важно:** документация описывает *возможности игры* и *возможности программы* раздельно. Наличие ID в каталоге не означает, что его механика, коллизии, отрисовка или сериализация специальных полей реализованы в `gdgen`.

## Реальные статусы

- **Подтверждено в GD:** уровень `AI Neon Run` вручную импортирован и пройден 2026-11-06. Уровень `Neon Cyber City` **запускается в игре**, но пользователь оценил его как **очень сложный**. Трудность/проходимость для других seed и пресетов не гарантированы.
- **Реализовано:** Python CLI, rule-based промпт RU/EN -> `LevelSpec`, детерминированные секции, Cube/Ship/Wave (с ограничениями), шипы/пады/порталы, базовый декор, цветовой триггер, городской декор, BPM-акценты без синхронизации с аудио; .gdlvl, JSON-sidecar, PNG, inspect, редактирование по спецификации, тесты и CI.
- **Только частичная/сырая поддержка:** `GDObject(id, x, y, props)` может записать известный ID и числовые/строковые свойства в level string. Это **не** готовый высокоуровневый генератор для всех объектов или триггеров. `preview` и `validate` знают лишь подмножество.
- **Ещё не реализовано:** симуляция физики и доказательство проходимости; полноценные Ball/UFO/Robot/Spider/Swing; настоящая Wave-траектория; адресное редактирование объектов; LLM-планировщик; анализ музыки, точный beatmap; полный движок групп/триггеров/шейдеров/камеры.
- **Проверка offline-импорта** через `CCLocalLevels.dat` после исправления `<d>` остаётся отдельной от успешного ручного импорта .gdlvl.

## Обязательные правила проектирования

1. **Играбельность важнее сложности и декора.** После замечания пользователя «очень сложно» *не* считать текущий Hard подходящим ориентиром. Следующий образец по умолчанию — Easy/Normal с увеличенными окнами реакции, понятными переходами и без внезапных ловушек. Не выдавать «Hard» за лёгкий.
2. Разделять **gameplay** (твёрдые блоки, шипы, пилы, порталы, реальные хитбоксы) и **visuals** (фон, надписи, свечение, градиенты, анимации). Не использовать обычный твёрдый блок как «декорацию», если он может создать непредвиденную коллизию. Уровень `gdgen/generator.py` пока использует `make_block` для части декоративных объектов — это требует проверки/исправления.
3. Для каждого игрового режима делать **свою** геометрию и правила ввода. Текущий fallback `else: _ship_section(...)` не означает поддержку Ball/UFO/Robot/Spider/Swing. Текущая Wave — широкий Ship-коридор, не расчёт движения Wave.
4. Порталы должны быть **достижимы** по маршруту; обеспечивать безопасную зону до/после смены режима, скорости, гравитации или размера. Если пользователь запросил первый режим не Cube, не утверждать, что он реализован: `generate()` стартует с Cube.
5. Предпочитать узнаваемые игровые конструкции и постепенно вводить сложность: обучение -> развитие мотива -> вариация -> пауза -> финал. Не повторять однотипный коридор или цепочку шипов на протяжении всей секции.
6. Не путать `Editor Layer` (свойство **20**) с **Z Layer** (свойство **24**) и **Z Order** (свойство **25**). У объектов в `city.py` сейчас используется `20: 3` — это редакторский слой, а не доказательство правильного порядка отрисовки. Проверять в игре.
7. У триггеров всегда проверять, что target Group ID/Color ID/Item ID существует, момент активации верен, флаги Spawn/Touch/Channel указаны осмысленно и эффект не ломает коллизию, камеру или читаемость.
8. **Не выдумывать** объектные ID, специальные свойства, значения enum, хитбоксы или физику. Для новых семейств сверить [каталог ID](docs/OBJECT_CATALOG.md) и [спецификацию полей](docs/TRIGGER_CATALOG.md), затем получить минимальный образец из редактора/публичного парсера и протестировать round-trip. Особо осторожно с ID 2.2/2.209.
9. **Нельзя утверждать «100% проходим».** `estimate_route` и `validate` эвристические; необходим игровой playtest для подтверждения. Предпросмотр PNG не является рендером GD.
10. Сохранить воспроизводимость: фиксированный `seed`, `LevelSpec`, версия, выходные файлы и тесты. `edit --out` не должен уничтожать исходный sidecar. Не создавать скрытые зависимости от внешних API.
11. **Безопасность:** не запускать GD, не изменять реальное `CCLocalLevels.dat`, Steam Cloud или пользовательские уровни без явной необходимости. Предпочитать штатный Import .gdlvl. Никогда не публиковать уровни в GD автоматически.
12. Рабочая ветка проекта — **`main`**, без отдельных PR по текущей договорённости. Перед коммитом выполнять `python -m unittest discover -s tests -v`, при изменении генератора — также `python -m gdgen generate ...` и `python -m gdgen inspect ...`.

## Схема решения задачи «сгенерируй уровень»

1. **План:** длительность (с), сложность и целевая аудитория, стиль, seed, режимы, скорость, музыка/BPM (с отличием указанных и реально измеренных).
2. **Blueprint:** секции с началом/концом, игровым режимом, механическим мотивом, вводом игрока, безопасными переходами, декором, акцентами; явно указать неизвестную физику.
3. **Game geometry:** блоки/платформы/шипы/орбы/пады/порталы; учитывать скорость, гравитацию, размеры хитбоксов, переходы и запас реакции. Если режима нет в движке — реализовать/протестировать, **не подменять Ship**.
4. **Visual pass:** независимые декоративные группы, каналы цвета, Z-слои, триггеры и повторно используемые мотивы; не закрывать игрока вспышками.
5. **Validation:** корректность формата и ID, уникальность групп/Item ID, статические проверки столкновений, предупреждения сложности; дополнительно ручной игровой тест. При сомнениях помечать `needs_playtest`.
6. **Output:** `.gdlvl` + `.json` + общий и детальный PNG; отчёт: сколько объектов, какой seed, что реально протестировано, какие неопределённости остались.

## Команды

```bash
python -m unittest discover -s tests -v
python -m gdgen generate --preset ai-neon-run --out levels
python -m gdgen generate --preset neon-cyber-city --out draft --preview-only
python -m gdgen generate --prompt "Неон, 30 секунд, легко, Cube и Ship" --out draft
python -m gdgen inspect levels/ai_neon_run.gdlvl
```

## Проверка реализации перед добавлением фичи

| Запрос пользователя | Что проверять |
| --- | --- |
| «Сделай легче» | `GAP_BY_DIFFICULTY`, тройные шипы, ширину Ship/Wave, переходы и запас времени; не только метку `difficulty` |
| «Добавь UFO / Ball / Spider» | собственный генератор режима, доступность порталов, новые проверки и playtest |
| «Хочу красивый фон» | классы декоративных ID, отсутствие физической коллизии, `24/25` и эффекты в игре |
| «Пульсация в ритм» | BPM, аудио-offset, реальные тайминги по скоростям; `city.py` сейчас добавляет лишь статические световые метки |
| «Двигающиеся препятствия» | Group IDs + Move/Rotate/Spawn, порядок триггеров, модель столкновений |
| «Под музыку» | явный song ID, BPM и offset; без аудиоанализа **не** обещать синхронизацию |
| «Редактируй этот участок» | `edit` пока регенерирует уровень; адресное редактирование предстоит реализовать |

## Принцип расширения каталога

Каталог в `docs/` — **практический индекс**, а не заявление, что тысячи возможных ID уже исследованы или доступны генератору. При добавлении объекта: (1) проверить ID в актуальной версии GD, (2) описать категорию/хитбокс/особые поля, (3) сделать минимальный тестовый .gdlvl, (4) проверить в редакторе/игре, (5) добавить генератор, preview и validator, (6) пометить статус `implemented` / `raw-only` / `experimental` / `unsupported`. Никакого включения произвольных ID по диапазону без проверки.
